# 路线图与验收门槛

当前：**M1 开发中：规格校验、编辑、确认和 JSON 导出已实现；provider 与真实模型验证待完成。跨平台验证以 GitHub Actions 的实际结果为准**。下列任务不等于已有功能，也不是排期承诺。

| 里程碑 | 工作 | 进入下一阶段的证据 |
| --- | --- | --- |
| M0 基础 | 产品与架构基线、本地项目壳、mock、测试与 CI | 本地验证通过；仓库可获取；远程 CI 结果已核对 |
| M1 规格与模型 | ModSpec schema、provider 配置、OpenAI-compatible 文本适配、本地模型测试、输出校验、计划确认 | mock 与至少一个真实 provider 完成同一组规格样例；格式错误、取消、超时和密钥保护测试通过 |
| M2 最小工程闭环 | 固定 Fabric 模板、普通物品与配方生成、差异审查、快照、隔离 runner、日志和源码/JAR 导出 | 模板版本及许可证记录完整；真实 Gradle 构建通过；导出哈希、失败恢复与最小游戏实测记录可查 |
| M3 可持续修改 | 有界修复、回滚、增量修改、任务事件、库存与配方预览 | 修改不会破坏上次成功版本；失败可解释；重启可恢复任务记录 |
| M4 美术与模型 | 用户资源导入、贴图能力适配、像素校验、3D 预览、bbmodel 文件互通 | 资源来源与许可可追踪；正确尺寸和路径；独立样例模组可运行 |
| M5 多端交付 | Windows / macOS / Linux 安装体验、环境诊断、可选桌面包装 | 各平台安装、首次启动、升级、数据迁移验收通过 |

## 第一轮待办顺序

1. 定义 ModSpec v1 与合法/非法样例，先覆盖一个普通物品及简单配方。
2. 用 mock 实现结构化规格流程，保留用户确认与假设。
3. 增加服务端 provider 配置和文本适配，不开放任意工具执行。
4. 选择 Fabric 模板固定提交；手动构建并检查生成 JAR，再设计代码生成器。
5. 确定并验证 runner 隔离方案后，才接入自动构建。

## 待决事项

- 具体文本模型：由用户自带；先确定一个可测试的 OpenAI-compatible 服务，不把某个商用模型写死。
- 图片和 3D：分别评估能力与许可证，不假设文本 API 同时支持。
- 桌面包装：当前本地浏览器先行，等 runner 与跨平台需求明确后再决定 Electron / Tauri 等选型。
- 首发目标调整：1.21.1 是验证起点，若 API 稳定性或用户样例要求变化，必须先更新需求和模板 ADR。
