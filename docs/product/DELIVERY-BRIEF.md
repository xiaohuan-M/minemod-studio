# MineMod Studio · 优化后的产品与开发任务书

## 目标

交付一个可以在用户电脑直接使用、完整公开源码、自带 LLM API 的 Minecraft 创作产品。最终范围以 AutoMods 公开介绍的全部能力为对照，重新设计交互、领域模型和扩展机制；以实际操作结果和可复现验证作为验收依据，不以页面按钮、生成示例或营销声明作为功能完成证据。用户要求完整产品，早期 MVP 或“本地优先”的设计选择不能自行缩小最终范围。

**2026-10-25 核对：0.5.0 尚未达到此目标。** [逐项对照](PARITY-MATRIX.md) 是当前完成情况的依据，覆盖实现、限制及未验证项；版本号不是完整交付的验收标记。官网未开放的桌面功能单列，不能与已上线能力混在一起。

主要用户不要求会写代码：描述想法、比较方案、继续对话修改、查看物品/方块/实体和配方、制作贴图与模型、审查与回退版本、真实构建、导出并安装作品。进阶用户可以检查完整源码、替换模型服务、修改素材、分享模板和资源、扩展新版本适配器。

## 产品原则

1. 本地优先：工程、对话、素材、运行记录保存在本机；默认不请求外部模型。缺少 API 时手工创作、导入与导出仍完整可用。
2. 自带服务：文本、图片、3D 的能力分别适配，允许不同供应商/模型，不假定一个 Chat Completions 端点支持全部协议。当前真实 API 联调按用户要求跳过，必须用契约模拟测试标明边界。
3. 所见可追溯：每次生成/修改对应用户指令、规格版本、工程快照、任务、日志与产物哈希；恢复不会覆盖旧的成功产物。
4. 完整交付：Java 目标真实编译、Bedrock 包通过结构与引用检查；只交付校验过的产物。编译、包验证、GameTest 与人工游戏实测分别记录。
5. 可维护：模块化单体；领域规则不依赖 HTTP/页面；生成器、模型服务、存储、构建器通过明确契约协作；统一 schema、可复现依赖、格式检查、自动化回归和贡献文档。
6. 版本诚实：目标由注册表声明；每个目标独立给出支持内容、模板版本与验证证据。公开资料所写的 1.7.10–26.3 不能直接变成本站兼容性承诺。
7. 开源独立：保留依赖许可证和素材来源，不复制私有源码/品牌素材。本地默认模式无需账号或积分；托管市场、跨设备、身份、线路与激励仍作为公开功能缺口保留，不能以离线目录、BYO API 或资源包迁移代替相应实现。可选服务模块应保持本地模式独立运行。

## 必须验收的使用链路

- 新用户：安装 → 启动检查 → 无 API 手工制作 → 素材 → 源码 → 编译/打包 → 下载。
- 模型用户：配置 → 显式测试 → 多方案选择 → 生成 → 持续对话修改 → 有界失败诊断/修正 → 新版本交付。
- 美术用户：文本/参考图 → 图像/像素草稿 → 调色与编辑 → 纹理化 3D/UV/装备变换 → 源文件与游戏资源导出。
- 项目维护：搜索/重命名/归档 → 完整备份/恢复 → 工程版本回退 → 资源复用与分享。
- 开源贡献：克隆 → 冻结依赖安装 → 检查 → 浏览器测试 → 新适配器契约测试 → 实际目标构建 → 提交与 CI。

## 完整交付门槛

上述链路需要覆盖当前缺失的端到端行为：真实制作清单与进度、版本 API 检索、代码/素材连续修改、自动素材绑定、授权后的自动构建和有限轮修复、每轮完整作品版本恢复、完整的模型/动画/穿戴集成、在线资源发布复用与跨设备续作。目标版本必须逐一有适配和证据；不能修改版本字符串后视为支持。

对照矩阵中的平台账号、积分和激励功能也必须明确处理；当前均未实现，不能记录为已完成。签名桌面版、Blockbench 自动化、自动启动游戏测试作为官网公开规划的独立验收项。

只有实现与验收同时满足，才能称为完整交付：真实模型效果、游戏行为、跨平台运行和复杂文件互通都有各自证据。真实 API 暂缓是用户当前明确允许的验证例外，不能扩展成省略产品能力。编译通过不等于游戏测试通过。

每个功能块完成后运行相关检查并提交、推送。网络/凭据/授权阻塞必须写明具体操作，继续其他可独立完成的工作；不把阻塞项标为完成。
